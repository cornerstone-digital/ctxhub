# Lerna example — validation fixture for the future Lerna `WorkspaceAdapter`

Real `npx lerna init` (modern Lerna 9, which delegates package linking to the package manager's own workspaces rather than managing symlinks itself), plus a real `"@example/core": "^1.0.0"` dependency, installed with real `npm install`. See [docs/monorepo_architecture.md](../../../docs/monorepo_architecture.md) §7: every future monorepo adapter must be proven against a repository actually generated by that tool's own tooling, not a fixture that guesses at the config format.

## What's here

- `lerna.json`, `package.json` (`workspaces: ["packages/*"]`) — real Lerna + npm workspaces config, exactly what `lerna init` produced.
- `packages/core` — `@example/core`, no dependencies.
- `packages/billing-service` — `@example/billing-service`, depends on `@example/core` via `"^1.0.0"`.
- `graph-output.json` — the real output of `lerna list --all --graph`, checked in as the snapshot a future adapter's test suite should assert against:
  ```json
  { "@example/billing-service": ["@example/core"], "@example/core": [] }
  ```
  That edge was produced by Lerna's own dependency graph command, not written by hand. Note: `--all` is required — Lerna's `list` filters out private packages by default, and these are private (as most monorepo packages are).

## What a real `LernaAdapter` should reproduce

Per `docs/monorepo_architecture.md` §4, `LernaAdapter.buildGraph()` run against this directory should produce:

```ts
{
  tool: 'lerna',
  projects: [
    { name: '@example/core', kind: 'package', path: 'packages/core' },
    { name: '@example/billing-service', kind: 'package', path: 'packages/billing-service' },
  ],
  edges: [
    { from: '@example/billing-service', to: '@example/core', kind: 'depends_on' },
  ],
}
```

`node_modules` is not committed (see `.gitignore`); regenerate it with `npm install` from this directory if you need to re-run `lerna list` yourself.
