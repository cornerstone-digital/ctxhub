# Rush example — validation fixture for the future Rush `WorkspaceAdapter`

Real `npx @microsoft/rush init`, two projects registered in `rush.json`'s `projects` array, then real `npx @microsoft/rush update` (Rush delegates its actual dependency linking to pnpm under the hood). The only hand edit to generated config: `nodeSupportedVersionRange` in `rush.json` was loosened from `>=24.11.1` to `>=18.0.0` so `rush update` would run against the Node version available in this environment — everything else is untouched Rush output. See [docs/monorepo_architecture.md](../../../docs/monorepo_architecture.md) §7: every future monorepo adapter must be proven against a repository actually generated by that tool's own tooling, not a fixture that guesses at the config format.

## What's here

- `rush.json` — real Rush config, with `packages/core` and `packages/billing-service` registered under `projects`.
- `common/config/rush/` — Rush's generated config directory (build-cache.json, command-line.json, version-policies.json, etc.), untouched.
- `packages/core` — `@example/core`, no dependencies.
- `packages/billing-service` — `@example/billing-service`, depends on `@example/core` via `"workspace:*"`.
- `common/config/rush/pnpm-lock.yaml` — the real lockfile `rush update` produced (Rush uses pnpm as its linking engine internally). Its `../../packages/billing-service` importer entry lists `@example/core` resolved via `link:../core` — that's Rush/pnpm's own workspace-link resolution, not written by hand.
- `graph-output.json` — the real output of `rush list --json`. Rush's own CLI doesn't expose dependency edges through `list` (unlike `nx graph` or `turbo run --dry-run=json`) — the edge evidence for this tool comes from the lockfile instead, referenced above.

`common/temp/` (Rush's install output — node_modules, its own copy of the lockfile, lock files) is gitignored by Rush's own generated `.gitignore`, same treatment as `node_modules` elsewhere in this directory; regenerate it with `rush update` from this directory if you need to re-run Rush commands yourself.

## What a real `RushAdapter` should reproduce

Per `docs/monorepo_architecture.md` §4, `RushAdapter.buildGraph()` run against this directory should produce:

```ts
{
  tool: 'rush',
  projects: [
    { name: '@example/core', kind: 'package', path: 'packages/core' },
    { name: '@example/billing-service', kind: 'package', path: 'packages/billing-service' },
  ],
  edges: [
    { from: '@example/billing-service', to: '@example/core', kind: 'depends_on' },
  ],
}
```

Note for the adapter implementer: since `rush list` doesn't surface edges directly, `RushAdapter.buildGraph()` will likely need to read `common/config/rush/pnpm-lock.yaml` (or each project's own `package.json` dependencies, cross-referenced against `rush.json`'s registered package names) to build the edge list — this fixture exists specifically so that approach can be validated against Rush's real lockfile output.
