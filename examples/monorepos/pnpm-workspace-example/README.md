# pnpm Workspaces example — validation fixture for the future pnpm `WorkspaceAdapter`

Real `pnpm init` (root + each package) plus a hand-written `pnpm-workspace.yaml` (the format is a two-line YAML file — there's no scaffolding command for it beyond that) and a real `workspace:*` dependency, installed with real `pnpm install`. See [docs/monorepo_architecture.md](../../../docs/monorepo_architecture.md) §7: every future monorepo adapter must be proven against a repository actually generated by that tool's own tooling, not a fixture that guesses at the config format.

## What's here

- `pnpm-workspace.yaml` — `packages: ["packages/*"]`.
- `packages/core` — `@example/core`, no dependencies.
- `packages/billing-service` — `@example/billing-service`, depends on `@example/core` via `"workspace:*"` in `package.json`.
- `pnpm-lock.yaml` — the real lockfile `pnpm install` produced. Note the `link:../core` resolution under `packages/billing-service`'s `importers` entry — that's pnpm's own workspace-link resolution, not written by hand.
- `graph-output.json` — the real output of `pnpm list -r --json --depth=1`, checked in as the snapshot a future adapter's test suite should assert against (absolute paths replaced with relative for portability; everything else is untouched pnpm output).

## What a real `PnpmWorkspacesAdapter` should reproduce

Per `docs/monorepo_architecture.md` §4, `PnpmWorkspacesAdapter.buildGraph()` run against this directory should produce:

```ts
{
  tool: 'pnpm',
  projects: [
    { name: '@example/core', kind: 'package', path: 'packages/core' },
    { name: '@example/billing-service', kind: 'package', path: 'packages/billing-service' },
  ],
  edges: [
    { from: '@example/billing-service', to: '@example/core', kind: 'depends_on' },
  ],
}
```

`node_modules` is not committed (see `.gitignore`); regenerate it with `pnpm install` from this directory if you need to re-run `pnpm list` yourself.
