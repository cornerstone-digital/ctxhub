# Monorepo tool examples

Real example repositories, one per monorepo tool, for validating the future `WorkspaceAdapter` implementations described in [docs/monorepo_architecture.md](../../docs/monorepo_architecture.md) (ROADMAP.md Milestone 17). Each was generated by that tool's own scaffolding/CLI — `npx create-nx-workspace`, `npx create-turbo`, real `pnpm`/`yarn`/`rush`/`lerna` commands, real `bazel query` — not hand-written to guess at a config format. See §7 of the architecture doc for why this matters: tool config formats drift across versions in ways a hand-maintained fixture won't catch.

Every example follows the same minimal shape on purpose, so the expected canonical `WorkspaceGraph` is comparable across tools: two packages, `core` (no dependencies) and `billing-service` (depends on `core`), with that one dependency edge produced by the tool's own dependency resolution — never written by hand — and captured in a checked-in `graph-output.*` snapshot.

| Directory | Tool | Real command used | Edge evidence |
| --- | --- | --- | --- |
| `nx-example/` | Nx | `create-nx-workspace`, `nx g @nx/js:library` | `nx graph --file=graph-output.json` |
| `turborepo-example/` | Turborepo | `create-turbo` (stock default example) | `turbo run build --dry-run=json` |
| `pnpm-workspace-example/` | pnpm Workspaces | `pnpm init` + `pnpm-workspace.yaml` | `pnpm list -r --json`, `pnpm-lock.yaml` |
| `yarn-workspace-example/` | Yarn Workspaces | `corepack use yarn@stable`, `yarn install` | `yarn workspaces list --json`, `yarn.lock` |
| `rush-example/` | Rush | `rush init`, `rush update` | `common/config/rush/pnpm-lock.yaml` (Rush delegates linking to pnpm; `rush list` doesn't expose edges) |
| `lerna-example/` | Lerna | `lerna init`, `npm install` | `lerna list --all --graph` |
| `bazel-example/` | Bazel | `bazelisk` (Bazel 9.1.1), real `BUILD.bazel` targets | `bazel query --output=graph 'deps(...)'` |

Each directory has its own README with the exact commands run, what was (and wasn't) hand-edited, and the expected canonical graph a real adapter should produce against it.

## What's deliberately not here

- **A `GenericGitRepositoryAdapter` example.** Per the architecture doc, the generic fallback has no tool-specific format to get wrong, so it needs no fixture — every workspace ctxhub already indexes today is implicitly one.
- **`node_modules` and other install-time output** (`.pnp.cjs`, `common/temp/`, `bazel-*` symlinks) — gitignored per example, regenerable by re-running that tool's own install command from within the directory.
- **Adapter implementations.** These are fixtures for adapters that don't exist yet. No `WorkspaceAdapter` has been built — see ROADMAP.md Milestone 17 for the trigger that starts that work.
