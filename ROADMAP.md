# Roadmap

## Shipped

- Multi-repo workspace config, repo discovery, and Git-aware indexing
- LanceDB-backed document/source index with full-text search (`ctxhub index` / `ctxhub search`)
- MemPalace as the default durable agent-memory provider, with a `local-json` fallback
- MCP server (`ctxhub mcp`) exposing `search`, `memory_status`, and `repo_list` as read-only tools
- Config-level lifecycle hooks (`hooks.postPull`, `hooks.postIndex`) and a real Git `post-commit` hook (`ctxhub repo hook`)
- Agent launch integration for Claude, Codex, and Copilot (`ctxhub agent <name>`)
- Installable skills/prompt files for Claude, Codex, Copilot, and Cursor (`ctxhub skills install`) — an ambient auto-invoked skill plus a dedicated `ctxhub-search` skill for explicit, argument-driven on-demand search (`/ctxhub-search <query>` in Claude Code/Codex), mirroring spec-kit's one-skill-per-action pattern
- Interactive onboarding wizard (`ctxhub onboard`) that composes init, repo discovery, hooks, memory, agents, and skills into one guided flow
- Live terminal progress/checklist views for `ctxhub index`, `ctxhub sync`, `ctxhub watch`, `ctxhub doctor`, and onboarding, with plain non-TTY output preserved for scripts
- Standard OSS project scaffolding: LICENSE, CONTRIBUTING.md, CODE_OF_CONDUCT.md, issue/PR templates
- Fully automated semantic versioning and changelog via semantic-release + Conventional Commits (npm publishing intentionally disabled until ready to ship)
- `ctxhub doctor` detects drift: outdated installed skills, outdated agent MCP configs, and config schema version mismatches, each with the exact command to fix it
- Automatic drift nudge on any command after a ctxhub upgrade (once per version, not on every command), via a Commander `preAction` hook
- `ctxhub agent <name>` also wires up MemPalace's own MCP server (`mempalace-mcp`) alongside ctxhub's when it's the configured memory provider and available, so agents get a real write-capable memory surface (`mempalace_add_drawer`, `mempalace_checkpoint`, etc.) for durable, personal/session notes
- `ctxhub note add <repo> "<title>"` scaffolds a dated, consistently-formatted note file under `<repo>/agent-notes/` for anything worth a teammate seeing and reviewing — git-tracked, shows up in the PR diff, and gets indexed like any other doc once merged. Distinct from MemPalace: this is for team-shared, review-worthy notes, not personal/session memory.
- Mermaid architecture diagrams are first-class context: `.mmd`/`.mermaid` files and fenced Mermaid blocks are indexed with extracted component/relationship metadata, `ctxhub diagram add` scaffolds git-tracked diagrams under `docs/architecture/`, and MCP exposes architecture-specific search/map tools.
- Agent context packs (`ctxhub pack` / MCP `context_pack`) combine search, architecture, freshness, repo list, and status into one agent-ready bundle.
- Exact context expansion tools (`open_chunk`, `get_file_context`) let agents move from search snippets to grounded source/doc context.
- Freshness metadata marks stale search results when repo HEAD or dirty state no longer matches the indexed commit.
- `ctxhub eval`, `ctxhub validate docs`, and `ctxhub graph` add search-quality checks, documentation validation, and architecture graph summaries.
- `ctxhub open`, `ctxhub pr-context`, `ctxhub watch`, and `ctxhub report` round out day-to-day review, development-loop, and workspace-report workflows.
- Privacy-aware indexing excludes environment files by default and redacts common secret-like values before storing chunks.
- Opt-in LLM-backed features (`llm.enabled` in config, off by default): shells out to whichever agent CLI (claude/codex/copilot/cursor) is configured/detected for one bounded, non-interactive task per feature. Always falls back to the existing non-LLM behavior with a clear notice when disabled, unavailable, or timed out — never invents evidence beyond what it was given. Covers: `ctxhub explain` synthesis, an onboarding orientation narrator, `ctxhub pr-context` contract-risk review, `ctxhub graph --drift` repair suggestions, `ctxhub handoff` summaries, `ctxhub note`/`diagram add --draft`, tailored globs for newly discovered repos, `ctxhub eval --agent-report`/`--suggest-queries`, standalone `ctxhub ask`, `search`'s `rewriteQuery`, and LLM-authored file summaries at index time for large files.
- Context compaction on the MCP surface: every tool response is auto-compacted (redundant full content dropped, TOON vs. compact JSON picked per payload), plus `maxTokens` budget trimming and an `excludeSeen` delta mode on `search`, and `context_pack` no longer double-ships a chunk that matches both its search and architecture sub-queries.
- `ctxhub report` gained an interactive knowledge graph view (repo/file/component/MemPalace wing-room nodes, click-to-inspect neighbors) alongside the existing filterable list view — still a single self-contained HTML file, no CDN, no new runtime dependency.
- `memory_search`/`memory_timeline` read tools (MCP + CLI) and `ctxhub memory add`/`diary` write commands (CLI always; MCP `memory_add`/`diary_write` opt-in via `ctxhub mcp --allow-memory-write`, a separate gate from `--allow-index`) are thin passthroughs to MemPalace's real search/timeline/drawer/diary engine (see "Not planned" below for why this isn't a second memory implementation). A real bug in the underlying passthroughs was found and fixed this session: `mempalace.mcp_server`'s internal functions (used by timeline/add/diary) redirect stdout for MCP-protocol hygiene, so their JSON result landed on stderr, unnoticed by the code that only checked stdout -- `extractJsonPayload()` in `src/memory/mempalaceCli.ts` now checks both.
- Memory workflow automation on top of the primitives above: `ctxhub memory add` auto-suggests a wing/room from existing rooms (best keyword overlap, falling back to a `notes` room under the current repo) when not given explicitly; `ctxhub memory checkpoint [note] --agent <name>` auto-assembles a session-checkpoint diary entry from the current git branch/recent commits; `ctxhub note promote <repo> <query>` copies a MemPalace hit verbatim into a new git-tracked team note (`promoted-from` frontmatter records provenance). All three are deterministic (no LLM involved) and layer on top of the existing search/diary/drawer/note primitives rather than adding new storage.
- `ctxhub review <topic> --as <persona>` unifies several already-shipped review primitives behind one named workflow. Personas are data (`.ctxhub/cache/review-profiles.json`, auto-seeded with the 5 built-ins -- `bug-hunter`, `contract`, `security`, `performance`, `docs` -- on first run), not a hardcoded switch: `kind: "contract"`/`"docs"` reuse `pr-context`'s `reviewContractRisks`/`graph --drift`'s `analyzeArchitectureDrift`+`suggestDriftRepairs` as-is; `kind: "generic"` is a freeform LLM persona defined entirely by its `focus` text, so a team adds a new reviewer (e.g. a naming-convention or API-style-guide reviewer) by editing that file, no ctxhub code change. Gated on `llm.enabled` with the same disabled/unavailable/timeout fallback (raw evidence bundle, not an error) as every other LLM-backed feature. Verified against a real `claude` CLI call on a deliberately-introduced command-injection vulnerability (built-in `security` persona) and a deliberately-introduced snake_case naming violation (a fully custom, non-built-in persona defined only in a JSON file) -- both correctly identified with citations.

- Internal refactor: `src/llm/harness.ts`'s `AGENT_CAPABILITIES` table is now the single source of truth for what "supporting a harness" means (MCP config writing, skill install, headless LLM invocation), replacing three independently-maintained agent-name lists in `agent.ts`/`skills.ts`/`runAgent.ts`. Pure consolidation, no user-facing behavior change -- `cursor` still has no MCP-config-writing support, now visible in one place instead of three.

- `src/context/confidence.ts`'s `computeConfidence()` scores a provenance-bearing item (0-1) from real, inspectable signals only -- source type weight, recency decay, doc/code agreement (does it still match current repo state, or a resolved source file's state), and count of independent corroborating sources -- never a model's own self-reported confidence, and never an LLM call. Wired into `ctxhub report`'s list badges and graph detail panel; not yet wired into `ctxhub review` since review findings aren't structured evidence items yet.

- Docs split into `docs/philosophy.md` (why), `docs/quickstart.md` (fastest path to first value), and `docs/architecture.md` (how it works), with `README.md` trimmed to a command/config reference pointing at all three. `examples/reference-workspace/` is a checked-in, pre-configured fictional 3-repo workspace (docs, one architecture diagram, two team notes) that works with `ctxhub index`/`search`/`graph`/`report` immediately after a clone, no external setup required.

- Faster indexing: `indexWorkspace`'s per-file "prepare" step (read, hash, redact, chunk, optional LLM summary) now runs concurrently across files (`index.concurrency` in config, default 8, batched to bound memory) via a small dependency-free `mapWithConcurrencyLimit()` helper -- I/O/subprocess-bound work, not CPU-bound, so real OS threads wouldn't have helped here. The actual write to the index provider still happens one file at a time, in original file order, since overlapping multi-step writes isn't safe for every `IndexProvider` (proven by a regression test against the non-locking `local-json` provider, which visibly corrupts its own file under concurrent writes if that serialization is ever removed). Measured a real ~2.4x wall-clock speedup indexing 300 files (80s -> 34s).
- `ctxhub watch` now reacts to real filesystem events (chokidar) instead of only polling on a timer -- a file change is picked up and re-indexed within its debounce window (300ms) rather than waiting up to `--interval` seconds; `--interval` remains as a periodic fallback pass, not the primary trigger. `--detach` runs it as a real background process (PID file + logs under `.ctxhub/cache/watch.{pid,log}`), with `--status`/`--stop` to check on and terminate it -- no OS-level service manager integration (launchd/systemd), matching the project's local-first/no-new-infrastructure bias.
- Desktop notifications (`--notify`, on `explain`/`ask`/`pr-context`/`handoff`/`review`/`eval --agent-report`/`--suggest-queries`/`index`/`sync`/`watch`): a thin, best-effort shell-out to the OS's own notifier (`osascript` on macOS, `notify-send` on Linux, a documented no-op on Windows) via `src/utils/notify.ts` -- no new dependency, same "reuse platform tools" pattern as `ctxhub report --open`'s browser launch. Never load-bearing: a missing/failing notifier silently no-ops rather than failing the command that triggered it.

- Persona system (`docs/personas.md` is the full review of the Portable Agent Persona Specification and the phased adoption plan): a new git-tracked `agents/` directory (`personas/*.md`, `policies/*.md`, `manifest.yaml`) loaded via `src/personas/persona.ts`. `ctxhub personas init` scaffolds it; `--as <persona>` on `explain`/`ask`/`handoff`/`review` frames the LLM-backed answer through a persona, with an optional, additive evidence-discipline policy layer that always applies and can't be loosened by persona preference (consolidating what used to be six separately-worded copies of the same instruction across `explain`/`handoff`/`note`/`review`/`eval`/`diagram`) -- empty/no-op until a team opts in. `ctxhub personas sync` compiles personas per harness via the same `AGENT_CAPABILITIES` table `skills.ts` derives from, extended with `nativeSubagents`/`projectInstructions`: all four supported harnesses have confirmed, documented native subagent support, each with a genuinely different file format compiled by its own function in `src/commands/personas.ts` -- `.claude/agents/<persona>.md` (Claude Code, YAML frontmatter, verified live against the actual `claude` CLI, which responded in the persona's own voice), `.codex/agents/<persona>.toml` (Codex CLI, TOML -- documented, but a live verification attempt surfaced a real caveat: the currently installed CLI build gates it behind an under-development feature flag), `.github/agents/<persona>.agent.md` (GitHub Copilot CLI, YAML frontmatter), and `.cursor/agents/<persona>.md` (Cursor, YAML frontmatter) -- see `docs/personas.md`'s Phase 3 for sources and per-harness verification confidence. `ctxhub doctor` detects drift between installed persona files and what the current source would compile (mirroring its existing skill/MCP-config drift checks exactly), with an opt-in `--fix --fix-personas` to recompile stale ones.

- Control plane, Phase 1 -- Workspace Registry (`docs/control-plane.md` is the full review and phased adoption plan for the orchestration pillar): `ctxhub workspace register [path] [--name]` / `list` / `remove` manage a user-level `~/.ctxhub/registry.json` pointer list (`src/workspaces/registry.ts`), overridable via `CTXHUB_HOME`. Each workspace still owns its own config/index/memory/personas exactly as today -- the registry only remembers where a workspace is and what it's called. Registering an already-registered path is a no-op (returns the existing entry); a second workspace can't reuse a registered name without an explicit `--name`; a workspace whose path no longer exists is flagged by `list`, never silently pruned. Live-verified: registered two real scratch workspaces, listed them, removed one, confirmed the on-disk registry at each step.
- Control plane, Phase 2 -- the control-plane service: `ctxhub service start` (detached background process by default, `--foreground` for debugging) / `stop` / `status` reuse `ctxhub watch --detach`'s exact PID-file/log-file pattern at user scope (`src/commands/service.ts`). A minimal HTTP API (`src/service/server.ts`, plain Node `http`, no new dependency) on `127.0.0.1:7342` exposes `GET /health`, `GET /workspaces`, and `GET /workspaces/:name/status` (the latter reusing `ctxhub doctor`'s own check functions, so a workspace's control-plane health can never drift from its `doctor` health). The WebSocket event stream from the original plan was deliberately descoped -- nothing yet produces an event worth pushing until Captains exist, so an event bus would be speculative infrastructure ahead of a real need; polling the HTTP API is enough for the Phase 3 Fleet-view UI. Live-verified against a real detached service process: started it, curled all three routes, stopped it, confirmed it was gone.
- Control plane, Phase 3 -- Mission Control's Fleet view: `GET /` on the Phase 2 service (`src/service/fleetView.ts`) serves a self-contained HTML/CSS/JS page (same "no CDN, no bundler" style as `ctxhub report`, just fetched live against the running service's own JSON API instead of a point-in-time snapshot) listing registered workspaces and their `ctxhub doctor`-derived health. Deliberately just the Fleet view -- the brief's other Mission Control sections (workspace canvas, captain chat, tasks, activity feed, reviews, knowledge graph, approvals queue) all depend on later phases that don't exist yet. Live-verified: started the real service, registered a workspace, confirmed `GET /workspaces` returns exactly what the page's client-side JS fetches and renders.
- Control plane, Phase 4 -- Execution Profiles: `executionProfiles` in config (`src/config/types.ts`, defaults to `{}`) binds a persona to a specific harness + model via `{ persona?, runtime, model?, tags? }` entries, extending the already-shipped persona system rather than replacing it. `runAgentPrompt` (`src/llm/runAgent.ts`) gained per-call `agent`/`model` overrides -- never silently swapped for another CLI, same discipline as the existing configured-agent path; `model` passes through as `--model` for claude and `-m` for codex (both verified against real `--help` output). `ctxhub explain --profile <name>` is the reference integration: `--as` always wins for framing when both are set, the profile's own `persona` is the default otherwise, and an unknown profile name throws immediately. Live-verified against the real `claude` CLI with a `runtime: claude, model: claude-haiku-4-5` profile -- got a real synthesized, cited answer.

## Planned

- AI-generated documentation validation
- Control plane, Phases 5-7 (`docs/control-plane.md`): orchestration is a first-class second pillar of ctxhub alongside the context/memory fabric -- a personal, customizable framework for running agentic workflows across workspaces, not a hedged-against extra. Next up: the Central MCP Gateway (Phase 5), then Fleet/Workspace Captains (scheduled/triggered task dispatch onto a workspace + persona + execution profile, still delegating actual model calls to a configured harness CLI) and gateway adapters like OpenRouter/Bedrock (Phases 6-7) last, since each phase is real infrastructure the next one builds on. `--profile` support on `ask`/`handoff`/`review` (following `explain`'s pattern) is also an easy, unscheduled fast follow.

## Not planned

- ctxhub reimplementing MemPalace's actual memory engine — `src/memory/mempalaceCli.ts` shells out to MemPalace's real CLI/Python internals (`mempalace.searcher`, `mempalace.mcp_server`) for every read and write; ctxhub never stores or parses durable memory itself. What ctxhub *does* now provide (revised again from an earlier, stricter version of this line): read-only `memory_search`/`memory_timeline` MCP tools and CLI commands, plus write commands (`ctxhub memory add`/`diary` always over CLI; `memory_add`/`diary_write` over MCP only when the server starts with `ctxhub mcp --allow-memory-write`, its own opt-in gate, separate from `--allow-index`) — all thin passthroughs to MemPalace's own engine, not a second implementation of it. `ctxhub agent <name>` still also wires up MemPalace's own full MCP server (`mempalace-mcp`, 19 tools) alongside ctxhub's, so an agent has both surfaces available.
- An embeddings/vector-DB index provider — lexical/full-text search already covers this project's typical doc+code corpus well, and a local embedding model would add a second native-binary dependency for modest benefit on identifier-dense content.

The embeddings decision was deliberately decided against rather than merely deferred. The memory-operations line above was revised, not reversed: ctxhub still doesn't own or reimplement memory storage — it just grew thin convenience wrappers around MemPalace's real engine.
